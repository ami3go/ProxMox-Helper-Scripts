Repository architecture

Provisioning stays local; infrastructure stays shared.

Per-helper ownership

Each helper owns one stable folder under helpers/<id>/, including its manifest, installer, files, modules, templates, assets, documentation, and tests.

Static registry

Literal metadata is validated without execution, then used by the launcher, catalog generator, Pages site, and release packager.

Shared primitives

Generic root checks, messages, menus, discovery, and execution live under lib/. Product-specific logic does not.

Central launcher

The same command lists, inspects, validates, and runs every registered helper from a TUI or normal CLI.

Generated documentation

HELPERS.md and docs/data/helpers.json are generated from manifests, preventing catalog drift.

Scalable releases

Tagged releases include the full repository, complete folder bundles for every helper, and optional standalone scripts for self-contained helpers.

Review standard

Helpers execute privileged infrastructure changes.

Every helper must validate its execution target, protect secrets, document side effects, use conservative exposure defaults, and provide a rollback or removal path. Review helper source before execution.

An LXC shares the Proxmox host kernel. Use a full VM for untrusted workloads, custom kernels, or stronger isolation boundaries.

  • Static, non-executable manifest metadata
  • Explicit destructive-action confirmation
  • Predictable rerun and repair behavior
  • No secrets in logs or repository state
  • Documented ports, files, and services
  • Tested rollback guidance
